# MessageHub (Local Messenger Hub)

Локальное Windows-приложение для объединения переписок из разных каналов связи в едином интерфейсе. Полное ТЗ — `docs/TZ_Local_Messenger_Hub.md` (главный источник требований — раздел 3, user stories US-XX; также ФТ-XXX — функциональные требования, БЗ-XX — требования безопасности). Схема БД (SQLite) — `docs/schema.dbml`.

## Стек и архитектура

.NET 10 (SDK 10.0.201, preview), C# 14, ASP.NET Core Minimal API.

Слоистая структура, решение — `MessageHub.slnx`:
- `MessageHub.Core` — доменные сущности (DDD-стиль): `Message`, `Person`, `UserProfile`, `ChannelContact`, `ConnectedAccount` + `Enums/`. Единственный слой с реальной логикой на данный момент.
- `MessageHub.Infrastructure` — пока пустой стаб (`Class1.cs`), предполагается EF Core / persistence.
- `MessageHub.Channels` — пока пустой стаб, предполагаются адаптеры каналов (Telegram/WhatsApp/…).
- `MessageHub.API` — ASP.NET Core хост; пока не связан с `Core` (нет `ProjectReference`), содержит только шаблонный `WeatherForecast`.
- `MessageHub.Core.Tests` — xUnit, тестирует только `Core` (единственный слой с логикой).

## Команды

- Установка/восстановление: `dotnet restore`
- Сборка всего решения: `dotnet build`
- Запуск API: `dotnet run --project MessageHub.API`
- Все тесты: `dotnet test`
- Тесты одного проекта: `dotnet test MessageHub.Core.Tests`
- Форматирование: `dotnet format` — **осторожно**: `.editorconfig` в проекте нет, поэтому `dotnet format` применит стандартный 4-пробельный стиль .NET, который разойдётся с текущим 2-пробельным стилем файлов в `Core`. Не гонять `dotnet format` по всему репозиторию бездумно — только точечно, и следить, чтобы дифф не перезатирал существующий стиль соседних строк.

## Соглашения по коду (видны в `MessageHub.Core/Entities/*.cs`)

- Отступ — 2 пробела (не стандартные 4 для C#). Соблюдать в новых файлах Core.
- Богатые доменные сущности: приватный конструктор + публичная статическая фабрика `Create(...)`, которая валидирует обязательные поля и бросает `ArgumentException` (`nameof(параметр)`). Все сеттеры приватные.
- Обязательные string-свойства валидируются прямо в property accessor'е через `field`-keyword (C# 14): `get; private set { if (...) throw ...; field = value; }`.
- Переходы состояния (например, `MarkAsSent`, `MarkAsDelivered`) проверяют текущее состояние и бросают `InvalidOperationException` при недопустимом переходе.
- Коллекции: приватный backing `List<T>`, наружу — `IReadOnlyList<T>`; мутирующие методы — на агрегате-владельце (см. `Person.AddChannelContact` / `ChannelContact` не создаётся напрямую).
- XML doc-комментарии (`///`) — на каждом публичном члене, включая `<exception>`; часто со ссылкой на пункт ТЗ (`US-08`, `9.6 ТЗ`, `ФТ-504`, `БЗ-02`) — при переносе логики из ТЗ сохранять такие ссылки.
- `Nullable` включён везде — не добавлять `#nullable disable`.
- Guid Id — `Guid.NewGuid()` внутри фабрики, не передаётся снаружи.

## Тесты

- `MessageHub.Core.Tests` — xUnit. Стиль: `Arrange`/`Act`/`Assert` без комментариев-разделителей, имя теста `Метод_Условие_РезультатОжидание` (см. `MessageHub.Core.Tests/Entities/MessageTests.cs`).
- Новая логика в `Core` (особенно валидация фабрик и переходы состояний) должна сопровождаться тестами в этом же стиле.

## Чего делать нельзя

- Не переносить `SecretRef`/пароли/секреты в явном виде в логи или доменные исключения (см. `БЗ-02`, `БЗ-03` в ТЗ).
- Не добавлять `ProjectReference` из `Core` на `Infrastructure`/`API`/`Channels` — зависимость только в одну сторону (наружу от `Core`).
- Не убирать приватные сеттеры и не открывать публичные конструкторы сущностей — вся мутация только через методы агрегата.
- Не запускать `dotnet format` без ревью диффа (см. предупреждение выше про 2 пробела).

## Рабочий процесс

Для многошаговых задач: **исследование → план → реализация маленькими шагами → проверка тестами (`dotnet test`) → коммит**. Веди `PROGRESS.md` (шаблон в корне) — обновляй его по ходу работы: текущая задача, чеклист шагов, что сделано, что дальше. Перед коммитом убедись, что `dotnet build` и `dotnet test` проходят.
