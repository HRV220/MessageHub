# commit-and-push

Автоматизирует обычный цикл «проверить → закоммитить → запушить» для этого репозитория, с гейтом сборки/тестов и подтверждением перед push. Вызывать только когда пользователь явно попросил закоммитить/запушить — сам по себе факт готовой правки не повод коммитить.

## Шаги

1. **Разведка** — параллельно:
   - `git status` (без `-uall`)
   - `git diff` (unstaged) и `git diff --staged` (если что-то уже застейджено)
   - `git log --oneline -5` — сверить стиль последних сообщений коммитов в этом репо (`type(scope): описание`, часто с указанием ФТ/US/T-NNN)

   Если рабочее дерево чистое (нет ни unstaged, ни untracked изменений) — сообщить об этом и не создавать пустой коммит.

2. **Гейт качества** — прогнать:
   - `dotnet build`
   - `dotnet test`

   Если что-то падает — **не коммитить**. Показать пользователю ошибку и либо исправить причину (если она тривиальна и очевидно связана с текущей правкой), либо остановиться и спросить, как быть. Никогда не коммитить заведомо красную сборку без явного разрешения пользователя.

3. **Стейджинг** — добавлять файлы поимённо (`git add <file> <file> ...`), никогда `git add -A`/`git add .`. Просмотреть список через `git status`, чтобы не затащить `.env`, ключи, файлы из `bin`/`obj` и т.п. Если находится что-то похожее на секрет — остановиться и предупредить пользователя, не коммитить.

   Если изменения логически распадаются на независимые темы (например, правка кода и отдельно правка документации/задач) — предпочесть несколько небольших коммитов одному смешанному, по образцу истории репозитория.

4. **Коммит** — сообщение в стиле репозитория: `type(scope): краткое summary` (типы, встречающиеся в истории: `feat`, `fix`, `docs`, `refactor`, `chore`, `test`), тело — 1-2 предложения о **почему**, а не о том, что и так видно из диффа. Не использовать `--amend` (кроме явной просьбы пользователя) и не пропускать хуки (`--no-verify`).

   Использовать heredoc для сообщения (см. правила git-коммитов в системном промпте) и заканчивать сообщение строкой атрибуции, которая задана в текущей сессии (обычно `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` — брать точный текст из системных инструкций сессии, а не хардкодить, если он там переопределён).

5. **Перед push — подтверждение.** Показать пользователю, что будет запушено (`git log origin/main..HEAD --oneline` или аналог для текущей ветки) и явно спросить подтверждение, прежде чем выполнять `git push`. Не пушить автоматически без этого шага, даже если исходная просьба уже содержала слово «пуш» — подтверждается именно момент отправки на remote.

   Исключение: если пользователь уже один раз в этом же сообщении явно одобрил и коммит, и пуш для конкретного, уже показанного набора изменений — можно не спрашивать повторно для этого же push.

6. **Push** — `git push` на текущую ветку с уже настроенным upstream (не force, не на произвольную ветку без спроса). Если push отклонён (remote ушёл вперёд) — не форсить, сообщить пользователю и предложить `git pull --rebase` либо разобраться в конфликте.

## Чего не делать

- Не коммитить без явной просьбы пользователя (см. корневой `CLAUDE.md`: «коммитить только если пользователь явно попросил»).
- Не пушить без отдельного подтверждения непосредственно перед отправкой.
- Не использовать `git add -A`, `git commit --amend`, `git push --force`, `--no-verify` без явной отдельной просьбы.
- Не коммитить, если `dotnet build`/`dotnet test` красные.
