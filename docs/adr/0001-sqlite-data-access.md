# ADR-0001: Доступ к SQLite — EF Core, маппинг вручную

## Статус

Принято, 2026-09-23.

## Контекст

Нужно выбрать технологию доступа к SQLite для `MessageHub.Infrastructure` (T-004). Требования, которые ограничивают выбор:

- **НФТ-10** — все данные приложения, кроме секретов, хранятся в одном файле SQLite.
- **НФТ-12** — схема создаётся и изменяется миграциями.
- **НФТ-13** — при каждом открытии соединения включаются `PRAGMA foreign_keys=ON, journal_mode=WAL, synchronous=NORMAL`, задан `busy_timeout`.
- **НФТ-14** — все выборки списков — с ограничением размера страницы, предпочтительно keyset-пагинация.
- **НФТ-21** — БД не загружается в память целиком.
- **НФТ-25** — чтение списков и лент — проекцией сразу в DTO ответа, без промежуточных доменных объектов.
- **НФТ-26** — маппинг без рефлексии (ручной или source-generated).
- **НФТ-27** — массовая запись при синхронизации — батчами в транзакции, без накопления отслеживаемых объектов.
- **АРХ-02** — `Core` не зависит от ASP.NET Core, SQLite, API-сервисов, UI, Windows API.
- **АРХ-08** — доступ к данным только через репозитории/запросы `Infrastructure`; SQL из контроллеров и UI запрещён.

Рассматривались три варианта:

1. **EF Core** (провайдер `Microsoft.EntityFrameworkCore.Sqlite`) — миграции из коробки, LSP-подобный DbContext, LINQ-проекции.
2. **`Microsoft.Data.Sqlite` + Dapper** — ручные SQL-запросы, ручной или Dapper-маппинг (Dapper использует рефлексию/`Expression`-кэш для маппинга колонок на объекты).
3. **`Microsoft.Data.Sqlite` напрямую (ADO.NET)** — полностью ручной SQL и ручной маппинг `DbDataReader` → объект, миграции — самописный раннер SQL-скриптов.

## Решение

Используем **EF Core** (`Microsoft.EntityFrameworkCore.Sqlite`) как технологию доступа к SQLite в `MessageHub.Infrastructure`, и **ручной маппинг** — без AutoMapper и без Dapper — на обоих направлениях:

- **Чтение списков/лент** (НФТ-25): репозитории строят LINQ-запрос с `AsNoTracking()` и явным `.Select(x => new SomeDto(...))`, который EF Core транслирует в SQL-проекцию — доменные сущности при этом не материализуются вообще. Это одновременно закрывает НФТ-21 (не грузим лишнее в память) и НФТ-14 (проекция сочетается с `.Skip/.Take` или keyset-фильтром).
- **Мутации и связь EF-модель ↔ доменная сущность** (НФТ-26): между EF-конфигурацией (persistence-моделью) и доменными сущностями `Core` — никакого reflection-based мапера. Маппинг «сущность → параметры EF» и обратно пишется руками в конкретных методах репозитория (или, при повторяющемся шаблоне в конкретной сущности, — source-generated partial-метод; выбор между «руками» и source-generated делается по месту при реализации репозитория, ADR фиксирует только запрет на reflection-based маппер).
- Миграции EF Core закрывают НФТ-12 «из коробки».
- `PRAGMA` (НФТ-13) выставляются в `DbConnection.StateChange`/при открытии соединения через `SqliteConnection`, до первого запроса на каждом соединении — не средствами модели EF.
- Батчевая запись при синхронизации (НФТ-27) — короткоживущий `DbContext`/явная транзакция на батч, `ChangeTracker.Clear()` после каждого батча, чтобы не копить отслеживаемые объекты.

`MessageHub.Core` по-прежнему не получает `ProjectReference` на EF Core и SQLite (АРХ-02) — EF Core живёт только в `MessageHub.Infrastructure`, наружу отдаются DTO/доменные объекты, а не EF-сущности.

## Альтернативы и почему отклонены

- **Dapper** — сам по себе не даёт миграций (пришлось бы добавлять отдельный раннер для НФТ-12), а маппинг результата на объект у Dapper по умолчанию идёт через кэшируемую рефлексию/`Expression.Compile` — не вписывается в «ручной маппинг» без дополнительной настройки под каждый тип. Не выбран, но можно пересмотреть точечно для горячих путей, если EF-проекции окажутся недостаточно быстрыми.
- **Чистый ADO.NET (`Microsoft.Data.Sqlite`)** — полностью удовлетворяет НФТ-25/26 «из коробки» (никакой магии), но собственный раннер миграций и ручной SQL для каждого запроса — существенно больше кода на дорожках 3–13 без явного выигрыша, раз EF-проекции и так позволяют держать чтение без промежуточных доменных объектов.

## Последствия

- В `MessageHub.Infrastructure` появляется `DbContext` с EF-конфигурациями таблиц по `docs/schema.dbml` (T-006).
- Репозитории для списков/лент пишут `.Select()`-проекции в DTO вручную — шаблонного авто-маппера (AutoMapper и т.п.) в проекте не будет.
- При заметном дублировании маппинг-кода для конкретной сущности — можно перейти на source-generated маппер для неё; ручной reflection-based маппинг остаётся запрещён в любом случае (НФТ-26).
- `PRAGMA`/пул соединений и миграции реализуются в T-005/T-006 на основе этого решения.
